# Отдельный профиль Kibana

Kibana 9.5.6 развёрнута с Elasticsearch той же версии в пространстве `logging`. 7 ноября 2026 года Pod был готов, `/api/status` вернул HTTP 200 и available, а `/login` был доступен через SSH-туннель с Windows. API data view и поиск для учётной записи читателя вернули HTTP 200, административный запрос — HTTP 403. Вход через браузер и просмотр в Discover ещё не проверены. Образ не закреплён по digest. Лимит Kibana 1 ГиБ и запрос 768 МиБ не подтверждают достаточный запас ресурсов на ВМ 5 ГБ. `emptyDir.sizeLimit` и `ephemeral-storage` не гарантируют мгновенную жёсткую квоту. [Результаты и ограничения](../../docs/test-results/stage-3-logging.md).

## Подготовка

1. Нужны здоровый Elasticsearch, Service `elasticsearch` порт 9200, CA в Secret `elasticsearch-http-ca` с ключом `ca.crt`, а также сертификат сервера ES с SAN `elasticsearch.logging.svc`. Сервисы должны быть доступны по TLS с проверкой имени и паролем административной учётной записи. Этот профиль не создаёт Elasticsearch или namespace.
2. Организуйте на защищённом сервере port-forward ES: `kubectl -n logging port-forward --address 127.0.0.1 service/elasticsearch 19200:9200`. Не открывайте этот порт на внешних интерфейсах. За пределами сервера используйте проверенный SSH-туннель. Пароль `elastic` и файл CA должны находиться в ограниченном каталоге вне Git; не выводите пароль, сертификаты и токены в чат или журнал. CA — открытый сертификат, но его целостность важна.
3. Для служебного доступа Kibana создайте отдельный token `elastic/kibana` через `create-service-token.py --password-file /защищённый/путь/password --ca-file /защищённый/путь/ca.crt --output /защищённый/путь/kibana.token`. Скрипт проверяет сертификат и SAN настоящего Service через порт 127.0.0.1:19200, токен не выводит; файл создаётся с режимом 0600 и без перезаписи. Если соединение прервалось после отправки запроса, проверьте и при необходимости отзовите token `kibana-logging` через ES API, прежде чем повторять.
4. `python3 create-config.py --token-file /защищённый/путь/kibana.token --output /защищённый/путь/kibana.yml` создаёт конфигурацию и три независимых ключа шифрования. Храните сам `kibana.yml` защищённо и с резервной копией: при утрате ключей зашифрованные объекты могут стать недоступны. Повторное создание файла отклоняется.
5. Создайте Secret из файла командой `kubectl -n logging create secret generic kibana-config --from-file=kibana.yml=/защищённый/путь/kibana.yml`. Она не должна печатать содержимое Secret. Существующий Secret не перезаписывается. Убедитесь в наличии обоих Secret и в адекватных правах доступа к ним в Kubernetes.

## Проверка и доступ

После проверки манифеста, подключений ES и свободных ресурсов профиль можно применить командой `kubectl apply -k <каталог-kibana>`; состояние проверяется через `kubectl -n logging rollout status deploy/kibana --timeout=900s`, `kubectl top pod -n logging` и память узла. HTTP probes показывают доступность страницы входа, но не доказывают корректность поиска. После проверки API остаётся проверить вход отдельной пользовательской учётной записью и просмотр логов в браузере; service token не является учётной записью пользователя.

Kibana имеет только Service ClusterIP, без Ingress и NodePort; политика запрещает Pod-to-Pod ingress. Проверенный доступ с Windows использует `logging/access/open-kibana.ps1` и SSH с проверкой ключа сервера; команда запуска и пути к имени и паролю читателя приведены в [основном README](../../README.md#логирование). В браузере открывайте `http://127.0.0.1:15601/` на стороне установленного туннеля. На участке browser → локальный конец и kubelet → Pod используется HTTP; между машинами применяется SSH. Ограниченная Kubernetes-учётная запись туннеля может создавать port-forward к Pod всего namespace `logging`: RBAC не позволяет ограничить это право по метке. Для доступа по сети без SSH необходимы HTTPS на стороне Kibana или защищённый reverse proxy и контроль доступа.

При проблеме остановите rollout командой `kubectl -n logging scale deploy/kibana --replicas=0` и проверьте восстановление существующих сервисов. Для постоянного удаления отзывайте отдельный service token через ES API и удаляйте только ресурсы этого профиля; данные Elasticsearch и другие namespace не затрагивайте. Полный сценарий удаления и восстановления не испытывался.
