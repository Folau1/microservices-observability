# Контролируемая проверка доставки логов

Этот сценарий предназначен для описанного в репозитории стенда `node2`. Он временно блокирует TCP-трафик **от Pod Vector к Pod Elasticsearch на порту 9200**, отправляет один запрос с недействительным токеном и затем восстанавливает связь. Проверка меняет живые правила firewall и создаёт событие в логах; запускайте её только вручную, когда такая краткая задержка доставки допустима.

Нужны Linux, root, systemd, `flock`, `iptables-nft`, K3s и работающие компоненты стенда с текущими именами и путями: namespace `logging`, Pod `elasticsearch-0`, каталог буфера `/var/lib/codex-elasticsearch/vector/buffer/v2/elasticsearch`, существующая конфигурация авторизации Elasticsearch в Pod. Необходимы отдельный смонтированный том логов, запас памяти и диска и исправная страница входа Kibana. Поддержка других конфигураций не проверена.

## Выполнение

Обычный запуск файла `guard.py` заблокирован. Чтобы явно запустить испытание, выполните **на узле Linux из корня проверенной копии репозитория**:

```bash
sudo python3 -c 'import sys; sys.path.insert(0, "logging/vector/tests/live-guard"); import guard; guard.experiment()'
```

Сценарий заранее создаёт отдельный systemd-таймер для точного удаления своего правила, затем следит за состоянием узла, памяти, томов и Kibana. При остановке или ошибке он пытается восстановить связь; если эта попытка не удалась, таймер остаётся действовать, а сервис очистки повторяет попытки. После перезагрузки временное правило исчезает, если другая программа не сохраняет и не восстанавливает firewall; отсутствие всех таких программ на произвольном сервере не гарантируется.

`BLOCKED` означает, что счётчик временного правила вырос, UUID тестового события найден в новых байтах дискового буфера и в этот момент событие отсутствовало в Elasticsearch; перед подтверждением повторно проверяются Pod и наличие правила. `RECOVERED` означает, что после удаления правила событие найдено в Elasticsearch, а страница входа Kibana отвечает. Это не доказывает fsync каждого события или отсутствие повторов позже. UUID запроса выводится для сопоставления событий; учётные данные и содержимое логов скрипт не печатает.

Если появится `MANUAL ACTION`, проверьте только собственные единицы `codex-vector-cut-*.timer`, соответствующий каталог `/run/codex-vector-cut-*` и правило с такой же уникальной меткой в `sudo iptables -w 5 -S FORWARD`. В каталоге находится `cleanup.sh`: он удаляет только точно совпадающее правило. Не отключайте таймер до подтверждения удаления правила; при ошибке сохраните вывод диагностики.

## Изолированные тесты

Тесты не обращаются к кластеру и используют поддельные `iptables` и `systemctl`. Для полной проверки гонок нужен Linux с Python 3 и `flock`:

```bash
python3 -m unittest discover -s logging/vector/tests/live-guard/tests -v
```

На системах без Linux-реализации `flock` часть тестов пропускается. Результат моков не заменяет проверку конкретного узла и его механизмов восстановления firewall.
