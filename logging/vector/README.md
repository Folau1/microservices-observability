# Vector: сбор логов

7 ноября 2026 года Vector был развёрнут и готов на `node2`. Два события security и uploader с одним `request_id` прошли через Vector в Elasticsearch. Это проверка отдельных событий, а не гарантия доставки при сбоях. Подробности — в [отчёте](../../docs/test-results/stage-3-logging.md).

Конфигурация читает структурированные JSON-записи security и uploader в namespace `microservices` на node2, оставляет только заранее перечисленные поля и отправляет их в data stream `logs-microservices-default`. Неструктурированные строки намеренно не пересылаются: они могут содержать чувствительные данные. Поэтому этот вариант не собирает все ошибки и логи; логи других приложений не собираются.

Сертификат CA находится в Secret `elasticsearch-http-ca`, ключ `ca.crt`, а учётные данные для записи — в Secret `vector-auth`, ключи `username` и `password`. Endpoint — `https://elasticsearch.logging.svc:9200`. Никакие секреты не включены в файлы репозитория. Сертификат сервера содержит этот DNS SAN. Секреты Kubernetes без дополнительной настройки не гарантируют шифрования на диске. Образ из официального GHCR закреплён digest amd64.

Vector использует дисковый буфер размером 512 МиБ и hostPath `/var/lib/codex-elasticsearch/vector` под checkpoints и буфер; каталог создан на отдельной файловой системе вместе с данными Elasticsearch. Тип hostPath `Directory` запрещает Kubernetes автоматически создавать отсутствующий каталог. Непосредственно перед развёртыванием на node2 обязательно выполнить `bash check-data-mount.sh`: он проверяет точку монтирования ext4 и расположение Vector на ней. Сам каталог создавать только после проверки монтирования; сохранять его отсутствие в корневом разделе под точкой монтирования. Этот preflight проверяет состояние на момент запуска, а не гарантирует сохранение mount при последующих административных действиях. Следить за занятостью общей файловой системы ES и Vector: `max_size` не является квотой общего объёма каталога. Source читает локальные Pod-логи best-effort: возможны потери и повторные записи. Под использует UID 0 для чтения hostPath и записи данных, но работает без capabilities и с read-only корневой файловой системой; возможность запуска без UID 0 следует оценить отдельно.

Локально прошли `kubectl kustomize`, `vector 0.61.0 validate --no-environment` и три теста трансформации с фиктивными секретами. На кластере подтверждены передача двух событий и ограничения учётной записи Vector; испытание дискового буфера при недоступности Elasticsearch не проводилось.
