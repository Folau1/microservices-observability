# План дальнейших работ

Приоритет — устойчивость существующей системы на одной VM с лимитом 5000 МБ. Перед каждым изменением и испытанием проверять свободную память, swap, место на обоих разделах, состояние приложения и мониторинга; фиксировать замеры и результат. Значения после последнего запуска — только моментальный срез, не гарантия запаса под нагрузкой.

1. **Исправить запуск после перезагрузки.** По событиям и журналам уточнить задержки старта MinIO, Security, Uploader и Telegraf, затем настроить `startupProbe` в их манифестах так, чтобы liveness не перезапускала ещё запускающийся процесс, а readiness по-прежнему исключала неготовый сервис из трафика. Для Traefik сначала проверить установленную версию Helm chart и поддерживаемые параметры, затем при необходимости настроить запуск через `HelmChartConfig`, не редактируя управляемый Deployment вручную. После изменений проверить rollout, probes и рестарты; Elasticsearch и Kibana уже имеют startup probes, их параметры также оценить по фактическому времени запуска.

2. **Обеспечить восстановление данных.** Подготовить защищённые резервные копии объектов MinIO, снапшоты Elasticsearch и копии необходимых ключей и секретов, включая CA и ключи шифрования Kibana. Хранить их вне Git и вне единственного диска VM; для Elasticsearch использовать поддерживаемый механизм snapshots. Проверить восстановление на отдельных данных без перезаписи действующих хранилищ и описать порядок восстановления и ротации ключей. Одна VM, один узел и `Retain` не заменяют резервную копию.

3. **Добавить контроль дисков и монтирования.** Настроить метрики и проверяемые оповещения о заполнении корневого раздела и отдельной файловой системы `/var/lib/codex-elasticsearch`. Для тома логирования отдельно проверять наличие правильного mount и его идентичность: при отсутствии mount нельзя принять корневой раздел за том логов. Проверить правила на имитируемых данных без демонтажа рабочего тома. Elasticsearch и буфер Vector делят 4 ГиБ; политика ILM ограничивает срок хранения, но не задаёт жёсткую квоту. Оба раздела находятся на одном физическом диске.

4. **Проверить восстановление доставки логов.** После подготовки копий и проверки запаса ресурсов провести короткое контролируемое испытание временной недоступности Elasticsearch: отправить события с известными `request_id`, восстановить сервис и проверить доставку и возможные повторы. Наблюдать размер буфера Vector, место на томе, память и доступность Kibana; условия остановки определить до испытания. Отдельно проверить поведение при длительном отказе и заполнении буфера без риска рабочим данным. Не обещать гарантированную доставку: возможны потери при переполнении и ротации исходных файлов.

5. **Подготовить HPA и умеренные испытания.** До масштабирования изменить сбор Prometheus с адресов Service на отдельные Pod или endpoints и проверить права: иначе скрейпы разных реплик могут смешивать счётчики и искажать скорости запросов. Затем настроить `autoscaling/v2` для одного stateless сервиса с CPU-метриками имеющегося Metrics Server и корректными CPU requests; начать с одной–двух реплик и задержки уменьшения числа реплик. Провести короткий ограниченный сценарий k6, заранее установив границы нагрузки и условия остановки. Зафиксировать RPS, среднюю и p95 задержку, ошибки, число реплик, CPU, RAM и swap; проверить возврат к одной реплике. Тяжёлую нагрузку без отдельного разрешения не запускать.

6. **Снизить расход ресурсов и проверить профили.** По фактическим измерениям подобрать requests, limits и порядок запуска, подготовить независимое включение мониторинга и логирования и проверить их совместную работу после перезапуска. Оценить потребление Elasticsearch и Kibana и только затем выбирать уменьшение ресурсов или более лёгкие варианты для будущего размещения. Возможность одновременного запуска всего текущего набора на VM с 2 ГБ пока не подтверждена.

После каждого этапа обновлять результаты проверок и инструкции в репозитории, указывая реальные ограничения и непроверенные сценарии.
