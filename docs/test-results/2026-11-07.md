# Проверка после перезапуска: 7 ноября 2026

Проверка выполнена на одном узле K3s после запуска виртуальной машины с верхним пределом памяти Hyper-V 5000 МБ. Ubuntu показывала 4,7 ГиБ общей памяти, около 2,6–2,7 ГиБ доступной памяти и 11 ГиБ свободного места на корневом разделе. Потребление меняется со временем.

- Узел Ready; все четыре Pod приложения и Pod Prometheus, Grafana и Telegraf были готовы. Контейнер агента TeamCity работал.
- Главная страница ответила HTTP 200 с Windows. Проверены вход с настроенной учётной записью и получение списка файлов: оба ответа HTTP 200. Секреты и токены в результаты не записывались.
- Запрос к списку файлов без токена вернул HTTP 401. После очередного опроса Prometheus содержал соответствующий счётчик запросов.
- Все четыре цели Prometheus находились в состоянии up, активных оповещений не было; проверка Grafana `/api/health` подтвердила доступность базы.
- Во время старта после перезапуска liveness probes временно не проходили у Traefik, MinIO и Telegraf, что вызвало перезапуски. На момент проверки они работали. Последнее состояние контейнеров не показало OOMKilled; это наблюдение не устанавливает причину всех прежних перезапусков.
- Frontend обновлён до образа `microservices-frontend:20261107-291fcc0`; новый Pod прошёл rollout и открыл обновлённую страницу. Архив образа сохранён в каталоге автоматического импорта K3s. Повторный перезапуск машины после обновления образа не выполнялся.

Elasticsearch, Kibana и Vector на дату проверки не разворачивались. Необходимо отдельно оценить пиковое потребление памяти и место под данные и буферы: размер PVC local-path не задаёт жёсткую дисковую квоту.
