# Этап 2: мониторинг

Дата: 5 ноября 2026 года. В namespace `observability` развёрнуты Telegraf, Prometheus и Grafana. Отчёт фиксирует фактические результаты проверок и моментальные значения ресурсов.

## Архитектура и доступ

Telegraf v1.40.2 считывает системные метрики узла через смонтированный только для чтения `/proc`, а доступные метрики узла и контейнеров — через kubelet API `https://<node-ip>:10250`. Проверка TLS выполняется с CA и токеном ServiceAccount; права ограничены `nodes/stats` и `nodes/pods` узла `node2`. Docker socket не используется. CPU, RAM, диск, сеть и доступные метрики Kubernetes получены из реальных источников. Проверки HTTP-готовности охватывают три сервиса приложения.

Prometheus v3.15.1 собирает метрики Security, Uploader, Telegraf и самого Prometheus. Проверены состояние всех этих targets `UP` и наличие данных. Grafana v13.3.0 использует Prometheus как источник данных. Сервисы наблюдаемости имеют тип `ClusterIP`; Ingress или публичный Service для их веб-интерфейсов не создавался.

Постоянное хранение: PVC Prometheus с запросом 2 ГиБ, PVC Grafana — 1 ГиБ. Для Prometheus заданы retention 2 дня и размер 768 MB. **Эти значения не задают жёсткую дисковую квоту:** local-path-provisioner не ограничивает занимаемое пространство, а WAL и данные в памяти могут привести к превышению порога retention. Необходимо контролировать свободное место корневого раздела и рост данных; это особенно важно для общей ВМ.

## Дашборды

- DevOps Dashboard — 11 панелей для системных ресурсов, доступности сервисов и HTTP-метрик.
- Business Dashboard — 7 панелей по реальным запросам и загрузкам. Для проверки использована реальная демонстрационная загрузка после запуска Prometheus; синтетические бизнес-данные не выдаются за метрики приложения.

Все 19 PromQL-выражений дашбордов проверены: каждое вернуло временные ряды. Наличие ряда не гарантирует наличие значимых данных за любой выбранный интервал.

## Alert

Правило `AppServiceDown` проверяет `up{job="apps"} == 0` в течение 30 секунд. Для контролируемой проверки во время теста был добавлен отдельный намеренно недоступный target `127.0.0.1:1`; для него наблюдалось состояние `firing`. Это тест с искусственным target, не реальный отказ бизнес-сервиса. После теста исходная конфигурация восстановлена, тестовый алерт отсутствует, скрипт завершился с кодом 0. Скрипт проверки: `monitoring/tests/test-alert.sh`; он временно меняет ConfigMap и должен запускаться только после согласования изменений Kubernetes. Внешняя доставка оповещений не настроена: Alertmanager отсутствует.

## Доступ к интерфейсам с Windows

Для подключения использовались SSH-туннели, проверенный host key и ограниченная учётная запись Kubernetes, а не административный kubeconfig. Проверка прав подтвердила возможность `create pods/portforward` и отказ в `get secrets` и `list pods` в namespace `microservices`. Kubeconfig и токен хранятся вне Git на сервере; срок действия токена, выданного при проверке, заканчивается **5 декабря 2026 года в 15:33 по времени Екатеринбурга** (10:33 UTC). После истечения токен нужно обновить; создание нового требует разрешённого административного доступа, а существующие файлы скрипт не перезаписывает.

При проверке публичный SSH-ключ для проекта был ограничен; для туннелей разрешены loopback-порты 13000 и 19090 через `permitopen` и `permitlisten`. Дальнейший аудит всех прав ключа не проводился.

Из корня репозитория на Windows в двух отдельных окнах PowerShell, подставив локальные пути к проектному SSH-ключу и файлу проверенных ключей сервера:

```powershell
.\monitoring\access\open-monitoring.ps1 -Service grafana -IdentityFile '<путь-к-ssh-ключу>' -KnownHostsFile '<путь-к-known_hosts>'
.\monitoring\access\open-monitoring.ps1 -Service prometheus -IdentityFile '<путь-к-ssh-ключу>' -KnownHostsFile '<путь-к-known_hosts>'
```

Оставьте окна открытыми и перейдите к `http://127.0.0.1:13000/` для Grafana и `http://127.0.0.1:19090/` для Prometheus. Оба SSH-туннеля и ответы через Windows проверены 5 ноября 2026 года; их текущее состояние и сохранение после перезапуска ПК не проверялись. При необходимости восстановите доступ указанными скриптами. Закрытие окна скрипта или Ctrl+C завершает соответствующий туннель.

Логин Grafana находится в `/home/codex/.local/state/microservices-observability/monitoring/username`, пароль — в соседнем файле `password`; файлы находятся вне Git. Пароль можно посмотреть **в консоли сервера**, выполнив `sudo cat /home/codex/.local/state/microservices-observability/monitoring/password`. Не отправляйте пароль или токен в чат и не помещайте их в репозиторий.

## Результаты и обнаруженные проблемы

До установки: доступно около 4,7 ГиБ RAM и 13 ГиБ на диске; TeamCity работал. Итоговый замер: узел — 2903 МиБ RAM (42%) и CPU 125m (4%); Grafana — 259 МиБ и 9m, Prometheus — 33 МиБ и 3m, Telegraf — 48 МиБ и 2m. По `free` доступно около 4,3 ГиБ RAM, свободно около 9,2 ГиБ на корневом разделе. Все три Pod мониторинга были Ready с 0 рестартов, приложение — 4/4 Ready, TeamCity — Up; алерт после теста inactive, сайт ответил HTTP 200. Это моментальные значения, не гарантированный ресурсный бюджет.

При первом запуске Grafana дважды перезапустилась: liveness срабатывал во время миграции SQLite. Добавлен `startupProbe` с бюджетом до 450 секунд; новая Pod Grafana запущена с 0 рестартов. При наблюдавшемся потреблении 353 МиБ рядом с прежним лимитом 384 МиБ лимит увеличен до 512 МиБ; request — 192 МиБ. Это не доказательство устойчивости при любой нагрузке.

Для самостоятельной проверки на сервере без вывода секретов:

```bash
sudo k3s kubectl -n observability get pods,svc,pvc
sudo k3s kubectl -n observability rollout status deployment/prometheus
sudo k3s kubectl -n observability rollout status daemonset/telegraf
sudo k3s kubectl -n observability rollout status deployment/grafana
sudo k3s kubectl top nodes
free -h
df -h /
```

В Prometheus через туннель проверьте **Status → Targets** и вкладку **Alerts**; в Grafana откройте оба дашборда. Установка и проверки проводились на компонентах этого проекта. Внешняя проверка firewall и проверка после перезагрузки сервера не проводились. Централизованное логирование, HPA и последующие этапы в рамках этого этапа не разворачивались.
