# Небольшая нагрузка API: 10 ноября 2026

Проверка k6 v1.8.2 выполнялась одним виртуальным пользователем: 20 итераций, 40 внешних HTTP-запросов. Запросы к Security и Uploader с намеренно недействительным токеном возвращали ожидаемый статус 401. Изменение файлов или реальных учётных данных не выполнялось.

Получено около 0,992 запроса в секунду; средняя длительность запроса — 8,09 мс, p95 — 16,38 мс. Ошибок не зафиксировано. После проверки HPA показывал одну реплику, Pod находились в состоянии Running; на узле было доступно около 900 МиБ памяти, использовано около 416 МиБ swap.

Это короткий тест отказа в доступе при очень небольшой нагрузке. Он не проверяет успешный вход, работу с файлами, масштабирование под пользовательским трафиком или поведение при высокой нагрузке. Результаты являются замером данного запуска, а не гарантией производительности.

Дополнительно после нагрузки проверены вход с действующей учётной записью и скачивание ранее созданного проверочного файла: оба запроса вернули HTTP 200, SHA-256 содержимого совпал с исходным. Новый объект не создавался.

Проверка Kibana через временный локальный port-forward: вход вернул HTTP 200 и создал сессию, представление данных логов ответило HTTP 200. Учётные данные в вывод не попадали.

Повторный запуск того же профиля с замерами: 40 проверок из 40 успешны, около 0,992 запроса/с, среднее 7,84 мс, p95 14,30 мс, ошибок нет. По периодическим выборкам `kubectl top node` CPU узла составлял 191–201m (6%), используемая память — 3642–3654 МиБ; доступная память по `free` — 908–947 МиБ, используемый swap — 403 МиБ. Это выборочные, а не пиковые значения.

По идентификатору проверочного запроса в Elasticsearch найдены три события: два Security и одно Uploader. Это записи отдельных вызовов и не является проверкой отсутствия повторной доставки.
