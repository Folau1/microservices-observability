# Этап 3: проверка централизованного логирования

Проверка выполнена 7 ноября 2026 года на существующем узле K3s с лимитом виртуальной машины 5000 МБ. Для данных логирования выделен отдельный том ext4 размером 4 ГиБ; Elasticsearch и буфер Vector используют каталоги на этой файловой системе. PersistentVolume настроен с политикой `Retain`.

На момент проверки Elasticsearch, Vector и Kibana были готовы: каждый Pod показывал `1/1`. HTTPS Elasticsearch с корректной авторизацией вернул HTTP 200, запрос без авторизации — HTTP 401. Отдельная учётная запись Vector успешно прошла аутентификацию с HTTP 200; попытка читать данные под ней получила HTTP 403, неверные учётные данные — HTTP 401.

Для сквозной проверки отправлены запросы к сервисам security и uploader с одним `request_id`. Соответствующие два события обнаружены в Elasticsearch: проверен путь от приложений через Vector до хранилища. Этот результат относится к выполненным запросам и не подтверждает отсутствие потерь при любых сбоях.

Kibana `/api/status` вернула HTTP 200 и статус available, страница `/login` с Windows через SSH-туннель — HTTP 200. Для учётной записи читателя API data view и поиск в Elasticsearch вернули HTTP 200; административный запрос был отклонён с HTTP 403. Вход через браузер и просмотр событий в Discover не проверены.

Elasticsearch сообщил состояние `yellow`: все 36 primary shards активны, одна replica индекса Kibana `.entity_analytics.watchlists.default` не распределена на единственном узле. Отсутствие места для replica на той же ноде ожидаемо; одна нода не обеспечивает отказоустойчивость.

## Ресурсы и восстановление

При замере Ubuntu показывала 4,7 ГиБ общей памяти, около 1,0 ГиБ доступной RAM и 311 МиБ используемого swap. На корневом разделе оставалось около 4,5 ГиБ, занято около 83 %. Значения меняются со временем; приложение, мониторинг, Elasticsearch и Kibana используют общую память ВМ, а образы и контейнерные логи продолжают занимать место на корневом разделе.

При параллельной загрузке Kibana K3s один раз перезапустился после ошибки `fatal SQL transaction commit`. OOM как причина не доказан. Образы затем загружались по одному при временно остановленном Elasticsearch; после восстановления Elasticsearch доступность и сохранность данных подтверждены. Перезапуск всей ВМ после настройки тома и логирования не выполнялся.

## Ограничения

- Elasticsearch и буфер Vector делят пространство выделенного тома. Размер PVC и политика хранения не являются отдельными жёсткими квотами для каждого компонента. 8 ноября добавлены правила Prometheus для контроля тома и корневого раздела; внешняя доставка оповещений не настроена. Заполнение тома логирования приведёт к ограничению записи и возможным потерям.
- Политика ILM предусматривает rollover по размеру или возрасту и последующее удаление старых индексов. Фоновое выполнение и рост индексов зависят от нагрузки: ILM не гарантирует точный общий размер данных или удаление в заданную секунду. Длительная работа политики и заполнение тома не проверены.
- Источник `kubernetes_logs` работает по модели best effort. Дисковый буфер снижает риск потери при временной недоступности Elasticsearch, но не гарантирует доставку при переполнении, ротации исходных файлов или сбое узла; возможны повторные записи. Остановка Vector, длительная недоступность Elasticsearch и поведение буфера при сбое не проверялись.
- Текущий запуск на ВМ с 5 ГБ не подтверждает достаточный запас памяти под длительную или пиковую нагрузку. Требуется наблюдать потребление, swap, рестарты и доступность остальных сервисов.
- Перезапуск ВМ, проверка монтирования тома после него, проверка бэкапа и восстановления данных после развёртывания не выполнялись.
