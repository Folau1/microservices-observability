# Проверка запуска Traefik

На узле K3s `node2` 7 ноября 2026 года `HelmChartConfig` с именем `kube-system/traefik` отсутствовал. Установлен пакетный chart `traefik-41.6.101+up41.6.1`; текущие readiness и liveness используют HTTP `/ping` на порту 8080. Файл `traefik-config.yaml` задаёт только startupProbe для того же endpoint: 36 попыток с интервалом 5 секунд и timeout 3 секунды. Во время startupProbe liveness и readiness ожидают её успеха; реальный срок старта нужно измерить. Полностью сломанный процесс не будет перезапущен до окончания этих попыток.

Проверен локальный рендер точной копии `/var/lib/rancher/k3s/server/static/charts/traefik-41.6.101+up41.6.1.tgz` (SHA-256 совпал с сервером). Helm 3.22.1 с фактическими `HelmChart.spec.valuesContent` и `spec.set` отрендерил до и после одинаковые манифесты за исключением startupProbe. Затем проверены применение Helm controller, rollout и фактический перезапуск узла: Traefik восстановился без дополнительных рестартов из-за liveness. [Результаты проверки](../../docs/test-results/2026-11-07-startup-probes.md).

## Применение после проверки актуального состояния

1. Сверьте состояние и ресурсы: `sudo k3s kubectl -n kube-system get helmchart traefik -o yaml`, `sudo k3s kubectl -n kube-system get helmchartconfig traefik --ignore-not-found`, `sudo k3s kubectl -n kube-system get deploy traefik`, `free -h` и доступность сайта. Если HelmChartConfig уже существует, сохраните его целиком, сравните изменения и аккуратно дополните его `valuesContent`, не заменяя чужие настройки. Убедитесь, что другой rollout или Helm job не выполняется.
2. Если объект всё ещё отсутствует, используйте `sudo k3s kubectl create -f traefik-config.yaml`. `create` безопасно откажет при одновременном создании другого объекта; не перезаписывайте существующую конфигурацию. K3s Helm controller запустит upgrade, вероятен краткий сбой ingress и дополнительная нагрузка в ограниченной по памяти VM. Не редактируйте пакетный `/var/lib/rancher/k3s/server/manifests/traefik.yaml`.
3. Дождитесь, пока `sudo k3s kubectl -n kube-system get deploy traefik -o yaml` покажет нужную `startupProbe`, и затем выполните `sudo k3s kubectl -n kube-system rollout status deploy/traefik --timeout=300s`. Нельзя полагаться только на немедленный `rollout status`: он может вернуть успех старого Deployment до начала Helm upgrade. Проверьте Helm job, Pods, события, ресурсы и HTTP сайта; при отказе исследуйте состояние до повторного запуска.
4. Проверка пробов после реального перезапуска и отсутствие преждевременного restart требуют отдельного наблюдения. Статический рендер и обычный rollout этого не доказывают.

## Откат

Если до работы пользовательский HelmChartConfig существовал, верните его сохранённую конфигурацию целиком и дождитесь применения. Если объект был создан только этой операцией, вместо удаления HelmChart или Deployment измените только `spec.valuesContent` этого HelmChartConfig на `startupProbe: {}` и дождитесь исчезновения startupProbe в Deployment и успешного rollout. Затем при необходимости удаляйте лишь HelmChartConfig и снова проверяйте ingress. Не удаляйте `HelmChart/traefik`: это может удалить сам Helm release. Если controller не пересогласует изменение, исследуйте его Job/состояние, не повторяйте команды вслепую. Удаление конфигурации из каталога автодеплоя K3s само по себе не является надёжным откатом ресурсов в кластере.
